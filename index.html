01 Architecture

A config-driven architecture for reusable data pipelines

A Data Pipeline Factory split across three connected GitHub repositories, one per layer. Scrapy handles source extraction, Airflow generates pipeline DAGs from YAML config, BigQuery stores raw payloads, and dbt turns them into trusted, typed models across bronze, silver, and gold layers.

02 Execution Lifecycle

How a scheduled run moves from extraction to transformation

On each scheduled run, Airflow launches source-specific ingestion DAGs, waits for successful completion, then runs dbt through Cosmos so every transformation model appears as its own observable task. Step through the six stages below.

Stage 01 · Orchestration

Airflow scheduler fires the spider DAGs

Airflow reads spiders_config.yaml and generates one independent DAG per spider automatically. No DAG files are written manually. Because each DAG is fully independent, a failure in one source does not affect the others. The same factory pattern works for any new source added to the config.

Apache Airflow Astronomer Astro spiders_config.yaml
Stage 02 · Containerisation

DockerOperator pulls the latest image from GHCR

Airflow runs each spider inside a Docker container using the latest scraper image from GHCR. This keeps orchestration cleanly separate from extraction code, and makes scraper updates available without touching any DAG files.

DockerOperator GHCR force_pull=True
Stage 03 · Extraction

Spider fetches data from the source

Each spider targets one endpoint and writes to the same ScrapedItem schema regardless of source. Credentials are passed via environment variables, never hardcoded. The raw payload is stored as a JSON string in the data field so the warehouse schema stays stable as sources evolve.

ScrapedItem api_spiders environment variables
Stage 04 · Storage

BigQuery pipeline batch-loads the raw data

When a spider finishes, buffered items are loaded to BigQuery in a single batch job, compatible with the free tier. Write mode is configurable per source: WRITE_TRUNCATE replaces the table on each run and is used when only the latest snapshot is needed. WRITE_APPEND accumulates rows over time and is used when historical data matters. Tables and datasets are created automatically on first run.

batch load · free tier WRITE_TRUNCATE auto-create tables
Stage 05 · Coordination

ExternalTaskSensors wait for all spiders to succeed

Before transformations run, sensors confirm that the required ingestion DAGs succeeded for the same logical date. This prevents dbt from ever transforming incomplete or stale source data.

ExternalTaskSensor mode=reschedule poke_interval=60s
Stage 06 · Transformation

Cosmos renders each dbt model as its own Airflow task

Cosmos parses the dbt project and renders each model as its own Airflow task. The full dbt dependency graph shows up directly in Airflow, making model-level failures easy to isolate and retry.

Astro Cosmos DbtTaskGroup DbtRunLocalOperator
03 Repositories

Repository separation by responsibility

Each repository owns a specific layer of the system: extraction, orchestration, or transformation. This separation means updating a spider never requires touching Airflow or dbt code, and updating a dbt model never triggers a Docker rebuild. Deployment boundaries stay clean, and each repo can be versioned, tested, and deployed independently.

04 Data Layers

Medallion architecture, from raw data to analytics-ready models

Every source follows the same modelling pattern. Raw payloads land first, then dbt progressively parses, types, cleans, and organises the data for analysis. Each layer has a clear contract: raw data lands untouched, bronze adds structure, silver adds trust, and gold adds business meaning.

Raw
Scrapers dataset · unmodified JSON
Every spider writes to the same raw schema regardless of source. The original payload is preserved as a JSON string in the data field, keeping ingestion flexible while standardising the warehouse landing structure.
run_idextraction_typedataexecution_datestart_dateend_dateendpoint
scrapers.*
Bronze
Bronze layer · parsed & typed
Parses raw payloads into structured, typed columns using a reusable flatten_json macro. No business logic is applied here.
brz_football.*
Silver
Silver layer · clean & business-ready
Cleans, deduplicates, and applies business rules to the Bronze data to produce analysis-ready models, structured as fact and dimension tables where applicable.
slv_football.*
Gold
Gold / Marts layer · aggregated for BI
The Gold layer holds aggregated, business-ready models for dashboards, KPIs, and advanced use cases.

05 CI/CD

Automated from code to container

Every push to the scrapers main branch triggers a two-job GitHub Actions workflow. No manual Docker commands, no manual deployments. The image is always in sync with the code.

Job 1
Test
1Set up Python 3.11 on ubuntu-latest
2pip install -r requirements.txt
3Create a dummy .env for CI, no real credentials needed
4scrapy check validates all spider class definitions
5pytest tests/ runs unit tests for items and settings
Runs on · pull_request + push to main
Job 2
Build & Push
1Log in to GHCR using the built-in GITHUB_TOKEN, no secrets to configure
2docker build packages scraper code + entrypoint.sh
3docker push to ghcr.io/madeleinehj/scrapers:latest
4Next Airflow run pulls the updated image automatically via force_pull=True
Runs on · push to main only
No manual deployment step. write spider → git push → Actions builds the image → next Airflow run pulls the container.
06 At Company Scale

What changes when this goes to production

The portfolio version keeps costs at zero while preserving the exact architectural patterns used in production systems. The config-driven DAG factory, the unified ScrapedItem schema, the medallion data model, the CI/CD image build on every push, and the sensor-gated dbt runs are all identical. What changes is purely the underlying infrastructure: managed cloud services replace local tools, but every engineering decision remains the same.

07 Next Steps

Where this platform goes next

Two enhancements that extend the same config-driven philosophy from ingestion into observability, catching data issues automatically and surfacing pipeline health at a glance.

01

Data Quality Check System

Using dbt tests to automatically detect data issues at every layer. When a test fails, Airflow catches it and sends a Slack notification to the responsible team with the exact problem and the steps needed to fix it.

dbt tests Airflow callbacks Slack alerts
02

Pipeline Monitoring Dashboard

A real-time dashboard tracking pipeline health across all sources: last successful run, row counts, data freshness, and failure history. Built on top of Airflow metadata and BigQuery audit logs, giving full visibility without opening the Airflow UI.
